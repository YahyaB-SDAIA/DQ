
# مشروع جودة البيانات (Data Quality Management Program) — https://athkax.sdaia.gov.sa سدايا SDAIA
## مجال البيانات: العملاء والحسابات البنكية للأفراد

> **تنبيه مهم:** هذا مشروع تدريبي توضيحي. جميع السجلات والنتائج اصطناعية بالكامل، ولا تمثل بيانات بنك حقيقي أو متطلبات رقابية تفصيلية. يجب مواءمة القواعد مع سياسات البنك، منتجاته، والاستثناءات المعتمدة قبل الإنتاج.

## 1. الملخص التنفيذي
تهدف الخطة إلى رفع موثوقية بيانات العملاء والحسابات المستخدمة في فتح الحسابات، خدمة العملاء، التقارير التشغيلية، والتحقق من صلاحية مشاركة البيانات بموافقة العميل. النطاق المقترح هو بيانات الأفراد والحسابات الجارية/الادخارية في بنك سعودي افتراضي.

**الأولوية المقترحة:** سلامة هوية العميل وربط الحساب به، ثم صحة IBAN وحالة KYC، ثم اكتمال بيانات الاتصال والموافقة. السبب: الأخطاء في الهوية والربط قد تنتج عنها مخاطر تشغيلية وخصوصية، بينما بيانات الاتصال تؤثر مباشرة على التواصل وتجربة العميل.

## 2. النطاق والافتراضات
- الكيانان الرئيسيان: `Customer` و`Account`، بعلاقة واحد إلى متعدد.
- لا يتضمن المشروع بيانات معاملات أو بطاقات أو ائتمان.
- القيم المرجعية مثل المدن والجنسيات والعملات يجب أن تُدار في جداول مرجعية مؤسسية.
- قواعد العمر والعملة والحالات في هذا النموذج افتراضات تشغيلية تعليمية، وليست نصوصًا تنظيمية.
- الفحص يعمل على ملف CSV اصطناعي، ولا يتصل بأي نظام مصرفي.

## 3. العناصر الحرجة مرتبة
1. **معرّف العميل الوطني** — أساس منع التكرار وربط السجل بالشخص الصحيح.
2. **رقم الحساب وIBAN** — أساس التوجيه والتحويلات والربط البنكي.
3. **حالة KYC وتاريخ آخر تحديث** — مؤشر اكتمال/حداثة إجراءات اعرف عميلك.
4. **حالة الحساب وتاريخ فتحه** — لتجنب التناقضات التشغيلية.
5. **رقم الجوال والبريد الإلكتروني** — قنوات الاتصال والتحقق.
6. **موافقة مشاركة البيانات المفتوحة وتاريخها** — للتحكم في المشاركة عند انطباقها.
7. **اسم العميل وتاريخ الميلاد والجنسية/المدينة** — للاكتمال وجودة الملف التعريفي.
8. **نظام المصدر والطابع الزمني للتحديث** — للتتبع وإدارة الحوادث.

## 4. نموذج الأدوار والملكية
| الدور | المسؤولية |
|---|---|
| مالك بيانات العملاء (Customer Data Owner) | اعتماد التعاريف والحدود والاستثناءات وقبول المخاطر |
| أمين بيانات العملاء (Data Steward) | متابعة النتائج، فرز المشكلات، التنسيق مع المصدر |
| مالك نظام المصدر (Source System Owner) | إصلاح التحويلات والتحقق عند الإدخال |
| فريق جودة البيانات | تشغيل الفحوص وإصدار البطاقة والتصعيد |
| الامتثال/الخصوصية | مراجعة قواعد KYC والموافقة والمواءمة النظامية |
| التقنية/تكامل البيانات | تنفيذ الإصلاحات الفنية وسجلات التشغيل |

## 5. كتالوج القواعد
يوجد كتالوج تفصيلي في `data_quality_pack.xlsx`، ويضم 18 قاعدة قابلة للفحص. القاعدة تعرّف البعد، الشدة، معيار الاجتياز، المالك، وتكرار التنفيذ. معيار القبول الافتراضي لكل قاعدة هو **100%** للحقول الحرجة، ويمكن لمالك البيانات اعتماد عتبة تشغيلية مختلفة موثقة لبعض قواعد الجودة غير الحرجة.

| المعرّف | القاعدة | البعد | الشدة |
|---|---|---|---|
| DQ01 | customer_id غير فارغ | الاكتمال | حرجة |
| DQ02 | customer_id فريد | التفرد | حرجة |
| DQ03 | national_id يتكون من 10 أرقام | الصلاحية | حرجة |
| DQ04 | national_id فريد | التفرد | حرجة |
| DQ05 | customer_name غير فارغ | الاكتمال | عالية |
| DQ06 | mobile بصيغة سعودية موحدة 05XXXXXXXX | الصلاحية | عالية |
| DQ07 | email بصيغة بريد صحيحة عند توفره | الصلاحية | متوسطة |
| DQ08 | تاريخ الميلاد صالح وعمر العميل 18+ | الصلاحية | عالية |
| DQ09 | account_id غير فارغ وفريد | التفرد/الاكتمال | حرجة |
| DQ10 | IBAN سعودي يبدأ SA وطوله 24 ويجتاز MOD-97 | الصلاحية | حرجة |
| DQ11 | IBAN فريد | التفرد | حرجة |
| DQ12 | account.customer_id موجود في العملاء | الاتساق المرجعي | حرجة |
| DQ13 | account_status ضمن القيم المعتمدة | الاتساق | عالية |
| DQ14 | الحساب النشط مرتبط بحالة KYC مكتملة | الاتساق | حرجة |
| DQ15 | open_date ليس في المستقبل | الحداثة/الصلاحية | عالية |
| DQ16 | consent_open_banking متسق مع consent_date | الاتساق | عالية |
| DQ17 | updated_at ليس في المستقبل | الحداثة | متوسطة |
| DQ18 | currency من قائمة العملات المعتمدة (SAR في هذا النطاق) | الاتساق | عالية |

**ملاحظة IBAN:** فحص MOD-97 يتحقق من بنية IBAN/checksum، لكنه لا يثبت أن الحساب موجود أو نشط لدى البنك.

## 6. التشغيل وإعادة الإنتاج
المتطلبات: Python 3.10+ و`pandas`.

```bash
pip install pandas
python quality_checks.py --input sample_data.csv --customers customer_master.csv --outdir outputs
```

المخرجات:
- `customer_master.csv`: جدول العملاء المرجعي المستخدم لفحص سلامة الربط.
- `outputs/check_results.csv`: نتيجة كل قاعدة وعدد المخالفات.
- `outputs/issue_log.csv`: عينة المخالفات على مستوى السجل والقاعدة.
- `outputs/run_log.txt`: ملخص وقت التشغيل والنتائج.
- `outputs/scorecard.csv`: بطاقة الأداء.

لتشغيل الفحوص على بيانات مصرح بها، استخدم نسخة منزوعة/مموهة الهوية، واحفظ النتائج في موقع محمي، ولا تضع أرقام هوية أو IBAN حقيقية في مستودع المشروع.

## 7. بطاقة الأداء
المؤشرات:
- نسبة الاجتياز لكل قاعدة = السجلات المجتازة ÷ السجلات المفحوصة × 100.
- الدرجة الموزونة = مجموع (نسبة الاجتياز × وزن الشدة) ÷ مجموع الأوزان.
- معدل المخالفات الحرجة = المخالفات في القواعد الحرجة ÷ مجموع فرص الفحص الحرجة.
- التغطية = عدد القواعد المنفذة ÷ عدد القواعد المعتمدة.

الأوزان المقترحة: حرجة 5، عالية 3، متوسطة 2، منخفضة 1. لا تخفي الدرجة الإجمالية إخفاق قاعدة حرجة؛ لذلك تعرض البطاقة حالات الإخفاق الحرجة منفصلة.

## 8. سجل المشكلات ومسار العمل
الحالات: `New → Triaged → Assigned → In Progress → Pending Validation → Closed`، أو `Accepted Risk` بموافقة مالك البيانات والامتثال عند الحاجة.
1. إنشاء مشكلة تلقائيًا عند وجود مخالفة.
2. تجميع المخالفات المتشابهة حسب القاعدة/المصدر.
3. تحديد الشدة والأثر والنطاق.
4. إسنادها إلى مالك المصدر أو أمين البيانات.
5. إصلاح السبب في المصدر، لا الاكتفاء بتعديل نسخة التقرير.
6. إعادة تشغيل الفحص والتحقق من عدم تكرار المشكلة.
7. إغلاق المشكلة مع دليل الإصلاح، أو قبول المخاطر بمدة انتهاء وموافقة موثقة.

## 9. تحليل السبب الجذري (RCA) — مثال واحد
**المشكلة:** ارتفاع مخالفات صيغة الجوال (DQ06) في سجلات قادمة من نظام CRM قديم.

**الأثر:** فشل رسائل التحقق/التواصل، وزيادة المعالجة اليدوية، وتراجع موثوقية بيانات الاتصال.

**تحليل 5 لماذا:**
1. لماذا فشل الفحص؟ لأن بعض الأرقام تحتوي على `+966` أو مسافات/شرطات أو بادئة غير موحدة.
2. لماذا وصلت بصيغ متعددة؟ لأن شاشة الإدخال القديمة تسمح بصيغ حرة.
3. لماذا لم توحّد عند التكامل؟ لأن واجهة ETL تنقل القيمة كما هي.
4. لماذا لم يُكتشف ذلك قبل الإطلاق؟ لأن اختبارات قبول التكامل اختبرت وجود الرقم لا تنسيقه.
5. لماذا لم تكن هناك ضوابط؟ لأن ملكية معيار صيغة الجوال وقاعدة التحقق لم تُحدد بين مالك CRM وفريق التكامل.

**السبب الجذري:** غياب معيار بيانات معتمد ومطبق عند نقطة الإدخال/التكامل، وليس خطأ المستخدم الفردي.

**الإجراء التصحيحي:** اعتماد معيار داخلي موحد، تطبيع الأرقام إلى `05XXXXXXXX` بعد التحقق من الدولة، رفض القيم غير القابلة للتحويل مع رسالة واضحة، وإضافة اختبارات عقد API.

**الإجراء الوقائي:** قاعدة تحقق في CRM وطبقة التكامل، مراقبة أسبوعية حسب المصدر، واختبار انحدار قبل كل إصدار. لا تُجرى إعادة كتابة تلقائية لأرقام ملتبسة دون تحقق.

## 10. خطة المراقبة
| النشاط | التكرار | المالك | عتبة/تصعيد |
|---|---|---|---|
| فحص قواعد الهوية وIBAN والربط وKYC | يومي | جودة البيانات + أمين البيانات | أي إخفاق حرج = تذكرة فورية |
| فحص الاتصال والموافقة | يومي | أمين بيانات العملاء | أقل من 99% = خطة إصلاح |
| بطاقة الأداء | أسبوعي | مدير جودة البيانات | انخفاض >2 نقطة أسبوعيًا = تحليل |
| مراجعة الأسباب المتكررة | شهري | مالك البيانات + ملاك الأنظمة | أعلى 3 أسباب |
| مراجعة الكتالوج والعتبات | ربع سنوي | مجلس حوكمة البيانات | اعتماد موثق |
| اختبار ضوابط المصدر | مع كل إصدار | مالك النظام | فشل الاختبار يمنع الإطلاق |

**اتفاقية مستوى الخدمة المقترحة:** المخالفة الحرجة تُفرز خلال يوم عمل، وتُحتوى خلال يومي عمل، ويُعتمد موعد إصلاح جذري خلال خمسة أيام عمل. هذه أهداف تشغيلية للمشروع وليست مددًا تنظيمية.

## 11. الدفاع أمام اللجنة الصورية
**اعتراض متوقع:** «لماذا نضع IBAN والهوية وKYC قبل اكتمال بيانات الاتصال؟ يمكننا تحسين تجربة العميل أولًا».

**الرد:** الأولوية مبنية على شدة الأثر وليس سهولة الإصلاح. خطأ الهوية أو IBAN قد يسبب ربطًا خاطئًا أو فشل تحويل أو إفصاحًا غير صحيح، بينما نقص الجوال يؤثر على التواصل ويمكن غالبًا احتواؤه بقناة بديلة. لا يعني ذلك إهمال الاتصال؛ بل نراقبه بعتبة 99% وخطة تحسين مستقلة. نقترح إعادة ترتيب الأولويات فقط إذا أظهرت بيانات البنك الفعلية أن أثر الاتصال أعلى أو أن مخاطر الهوية/IBAN محكومة بضوابط تعويضية مثبتة.

**متى نغيّر الأولوية؟** عند وجود قياس أثر موثق، تحليل حجم/تكلفة الحوادث، ومتطلبات أعمال أو امتثال معتمدة. لا تُغيّر الأولوية بناءً على الانطباع وحده.
